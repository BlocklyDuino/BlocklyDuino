Grayscale and RGB images on SD

Use Project devices → your SD card → Images → new image after adding an SD card with Add device. Select a file format and either sequential pixels or coordinate edits. Width, height, levels and pixel values are sockets: insert numbers, variables, array values, sensor readings or calculations.

Levels per channel is a count. With 1024 levels, valid pixel values are 0..1023. With 65536 levels, they are 0..65535. Zero is black; the highest value is white or full intensity for an RGB channel. All image dimensions, level counts and samples are whole numbers. Fractional, negative or out-of-range values are rejected rather than silently truncated, clamped or wrapped.

The upper limit of 256 applies to the indexed/24-bit BMP encodings implemented here. To save a 10-bit ADC value without reducing it to 8 bits, choose PGM or PPM with 1024 levels. The header records a maximum sample value of 1023, and every sample uses two bytes. A 1024-level RGB image retains 10 meaningful bits in each channel.

PGM/PPM write the supplied integer samples without automatic gamma correction or normalization. Some viewers display a lower-precision preview, but the file still contains the original values. Sequential pixels: keep only the current measurement

  1. In setup, create the image with sequential pixels. This replaces the named file and writes the header.
  2. As measurements arrive, call append gray pixel or append RGB pixel. The next position advances left-to-right and top-to-bottom.
  3. After exactly width × height pixels, call finish image.
  4. Check image OK after creation, writes and finishing.

A full image is never allocated in RAM. For example, a 128×128 PPM with 1024 levels has 98,304 bytes of pixel data, but the Arduino processes one pixel at a time. The SD library still needs its sector cache; image dimensions affect file size and write time rather than requiring a matching RAM image.

Use append gray pixel with a grayscale format and append RGB pixel with an RGB format. RGB values have separate sockets so each channel can come from a different calculation. The writer handles row boundaries and file byte order.

If a scan ends early, finish pads missing pixels black and reports false. Writing beyond the planned pixel count is rejected. An actual SD error can prevent completion, so a readable file is not guaranteed after an I/O failure.

Coordinate edits: write selected x/y positions

Select coordinate edits when points arrive in arbitrary order, such as a radar sweep mapped to Cartesian coordinates. Creation fills the file black first; after that, use gray pixel at or RGB pixel at. Coordinates start at (0,0) in the top-left. The library seeks directly to the corresponding file bytes; it still needs no framebuffer.

Coordinates and sample values accept variables. Use the action matching the format. Finish the image when editing is complete. Coordinate writes can be slower than sequential writes because they involve seeks and sector updates.

Variables, precision and file handling

On ATmega168, ordinary int is only 16 bits. For a level count that may reach 65536, declare uint32_t or unsigned long. Use uint16_t for samples through 65535, or int32_t when calculations may go negative. Avoid overflowing a 16-bit intermediate multiplication before passing it to the image block.

The PGM and PPM examples deliberately use a uint32_t levels variable. Their calculated samples reach 1023. Replace the gradient calculation with a sensor reading or array lookup to record measurements. Each example runs once in setup and lights D13 after a successful finish.

Keep the filename extension consistent with the selected format. The card uses short 8.3 filenames, such as SCAN.PGM or COLOR.PPM. New image replaces an existing file of the same name. The SD card has one active file handle: finish the image before opening another file or starting an SD melody.

Reserve space? optionally requests contiguous file space up front. This does not allocate image RAM. Reservation can fail when a large enough contiguous area is unavailable; check image OK. Dimensions, file-size arithmetic and sample ranges are validated at runtime, including when supplied through variables.

Existing projects

Earlier BMP blocks remain loadable. Their black/white and grayscale programs keep their original behaviour. The Images category is the shared entry point for new grayscale and RGB projects; it adds wider-range formats without changing existing SD text files or SD melody playback.

Validation and ATmega168 memory

The generated examples compile for Pro Mini ATmega168 at 16 MHz. RGB BMP uses 12,296 bytes of flash and 736 bytes of global RAM; PGM1024 uses 12,282/738; PPM RGB1024 uses 12,418/740. That leaves about 284–288 bytes for the stack and local variables, so a larger image file does not cost more image RAM, but additional libraries still matter. Coordinate-mode variants also compile. XML save/reload and SD-device renaming preserve the generated programs.

These checks validate generated code and file-format logic. They do not establish the performance or reliability of a particular physical SD card and module.
