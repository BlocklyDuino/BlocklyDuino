Memory, SD files and BMP images

Give each device a name in Devices, outside setup and loop. Set its address or CS pin once. Every operation selects that name. Changing a name preserves the references, including after saving and reopening the XML. Missing definitions cause a generation error.

Store numbers and long text

  1. Put a typed write in setup, or at the event when a setting changes.
  2. Choose a byte address. On AVR, byte/bool uses 1 byte; int16/uint16 uses 2; int32/uint32/float uses 4. Leave enough space between records. Read with the same type and address.
  3. Write text stores the characters followed by a zero byte. For example, reserve address 0 for a uint16 setting and address 16 for text.
  4. Read text returns a String up to the numeric max chars input, which can be a variable. For longer text, stream text to Serial sends bytes directly without storing the whole text in RAM.
  5. Check last operation OK. It reflects only the most recent operation, so check before starting the next one.

EEPROM updates unchanged bytes without writing them again. The drivers use byte writes with completion polling and read-back verification; they do not accidentally wrap at a page boundary. Operations are synchronous and long text writes take time. Keep records inside capacity: a write that crosses the end can leave a partially updated record. These helpers do not provide transactions or power-loss recovery.

SPI NOR flash can program a bit from 1 to 0. To change it back, use erase 4 KB sector first: it clears all records in that sector to 0xFF. The address selects the containing sector. Keep frequently changed settings in EEPROM instead, or design a log with unused flash slots. Erase waits for completion; it does not scan and verify the entire sector. Existing chip protection bits are not changed by these blocks.

Typed data is binary in the board's native representation. It is not a portable text file or a guaranteed format across every processor. Printed SD text is better for files intended to be read on a computer.

SD files

The installed SdFat 2.3.0 library provides FAT16/FAT32. These blocks use one card, one file and short names such as DATA.TXT. Use open file → append / read-write, print to file, then flush at a checkpoint and close when done. Opening another file closes the current one, except while a sequential BMP stream is active; finish that stream first.

For structured binary records use write binary and read binary with matching types. Seek selects an absolute byte position. Append mode starts at the end but permits repositioning; subsequent writes can overwrite existing bytes. Read byte returns −1 at EOF and allows long files to be processed one byte at a time. There is no exFAT or multiple-file block in this version.

Choose grayscale levels and calculate pixel shades

The same create BMP and start BMP stream blocks now have a gray levels value socket. Insert a number or a variable from 2 to 256. Both coordinate-based pixels and sequential pixels have a numeric shade socket: 0 is black, levels−1 is white, and intermediate values are gray. Variables, arithmetic and sensor calculations can feed these sockets directly. Levels are captured when the file is created; changing the variable later does not rewrite the existing palette.

The palette has exactly the selected number of entries, evenly spread from black to white. Its bytes are written directly to SD; even a 256-level palette is not stored in RAM. The file header and palette occupy 54 + 4 × levels bytes. Pixel rows are padded to a multiple of four bytes. Shades must be integer indices in 0..levels−1; out-of-range values are rejected rather than wrapped. Packed pixels use the same palette indices.

Change the grayLevels variable to 16 or 2 to use the other formats. Its 65 × 32 dimensions deliberately include row padding. The exact generated example compiles for ATmega168: 12,072 bytes flash and 718 bytes static RAM, leaving 306 bytes for stack and temporary data.

Write a BMP sequentially

Use start BMP stream → append BMP pixel / append packed BMP pixels → finish BMP stream when measurements arrive in image order. Pixels run left-to-right, then top-to-bottom. The start block writes the header and palette without filling the image. Pixel packing follows the chosen bit depth; row padding and an incomplete final byte are handled automatically. There are no per-pixel file seeks or reads.

Append BMP pixel accepts a numeric shade or a variable. Append packed BMP pixels consumes the highest packed pixels of a byte, most significant first. Pixel count is also a value socket: up to 8 pixels at 1 bit, 2 at 4 bits, or 1 at 8 bits. For example, with 16 levels, byte 0xA5 and count 2 append shades 10 and 5. A group may cross a row: padding is inserted without consuming any input pixels. Legacy saved bit groups preserve their earlier black/white behavior.

The two-level extension keeps one partial pixel byte, two position counters and state: 6 extra bytes on AVR. The runtime grayscale class adds palette/packing metadata for 11 bytes beyond the basic card/file object. SdFat already has a 512-byte sector cache. Feeding one byte at a time fills that cache; it does not send a separate SD transaction for every pixel. There is no second 512-byte application buffer or image array. File data is sequential; FAT metadata still needs separate updates. Card firmware can pause during writes, so this is not a guaranteed timing source.

Give exactly width × height pixels. Extra pixels are rejected without extending the file; an oversized bit group is rejected before consuming any of its bits. Finish closes the image. If too few pixels arrived, it fills the rest black to produce a readable file and reports last operation OK = false. A rejected operation also makes finish report false. An SD I/O failure can still leave an incomplete file. Regular close file also finishes an active stream. Arbitrary seek/read/write and opening another file are blocked until the stream is finished.

Flush at occasional checkpoints, not after each pixel. The partial pixel byte stays in RAM until its packed byte is full, its row ends, or finish is called. A flush cannot make an unfinished image complete. Finish includes the final sync; it can take longer when it has to pad a large unfinished image.

Reserve the complete file first

The start block offers grow file as needed or reserve contiguous space. Reservation calls SdFat preAllocate(54 + 4 × levels + rowStride × height) on the new empty FAT file. It finds and allocates a contiguous cluster chain before writing the header; if no suitable free region exists, the operation fails instead of silently falling back. It does not allocate a matching RAM buffer.

In the installed SdFat 2.3.0 FAT implementation, preallocation immediately sets the full logical file size. The reserved area initially contains uninitialized card data; writing every pixel, or the black padding at finish, replaces it. An interrupted reserved file must not be treated as a finished image. Without reservation, logical file length grows as bytes are appended. Both modes keep a normal FAT16/FAT32 file readable on a computer after a successful finish.

Writing after the highest used card address would not by itself allocate a FAT file. The filesystem also needs free-cluster allocation, cluster links, a directory entry and the correct length. Deleted files can leave holes, and unregistered raw writes may later be overwritten by the filesystem. This implementation uses SdFat for those records; it does not invent a second allocator alongside FAT.

Choose sequential output when the source naturally produces complete rows. A rotating radar produces sparse points by angle; plotting those points into a Cartesian image in arbitrary order still needs the earlier BMP pixel x/y method, or a later conversion of a recorded scan. A sequential image is also practical with angle on one axis and distance on the other, if each row can be produced in order.

Read a known file or inspect the card

To read a known file, use open file → read only with its name, then repeatedly read byte until −1, or read binary with the matching record type. The entire file and directory do not have to fit in RAM. List SD files to Serial prints root-directory short 8.3 names one at a time, using a 13-byte name buffer. Close the current file first. Serial itself consumes RAM on AVR, so keep this inspection sketch separate from a nearly full ATmega168 radar.

Update BMP pixels by coordinates

Create BMP replaces the named file with a black grayscale image using the selected levels. A 128 × 128 image with two levels occupies 2,110 bytes on the card; the Arduino holds no image framebuffer. BMP pixel reads and updates the relevant byte on the card. Coordinates start at the top-left; shade 0 is black and levels−1 is white. The shade socket accepts a variable or calculation. Dimensions and coordinates must be positive/in bounds; invalid pixel operations report false.

Create the image once in setup. Then measurements can add pixels gradually; flush periodically to commit them. Close after the scan. Random pixel updates are slower than RAM drawing and an SD write may block briefly, so this is a logging approach, not a high frame-rate display.

Radar scan written in measurement order

Example 40 · Polar scan BMP records a 128 × 61 image directly from a servo and ultrasonic sensor. Row 0 is 0°, row 1 is 3°, continuing to row 60 at 180°. Column 0–127 is distance in centimetres. Each row contains one white pixel at the measured distance; invalid readings and distances outside 1–127 cm leave the row black. The reading is converted to an integer centimetre.

The servo moves, waits 80 ms, reads once, then appends 128 pixels. Every row is generated from that one measurement; there is no trigonometry, image array, image prefill or per-pixel seek. This is an angle/distance chart, not a semicircular Cartesian radar picture. POLAR.BMP is 1,038 bytes. The scan runs once in setup and finishes the file; resetting starts again and replaces it. Connections: servo D9, trigger D5, echo D6, SD CS D10. Reservation defaults off to keep the build smaller.

The example compiles for ATmega168 using 13,532 bytes flash (94%) and 748 bytes static RAM, leaving 276 bytes for stack and temporary data. Hardware movement, settling time and SD latency still need checking on the real setup. Serial logging or more libraries would reduce that remaining space.
